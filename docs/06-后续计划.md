## 阶段 B · 多帧输入（最大的一块工程，也是唯一的必经之路）

**问题**：OpenVLA 是**单帧**模型。方案的全部价值在历史帧上，
但冻结模型没见过多帧输入，**这一步开始必须训练**。

需要做的：

1. **数据**：`bash scripts/prepare_finetune.sh data` 下载
   HF 上的 `openvla/modified_libero_rlds`（脚本会先报体积并检查磁盘再动手，
   支持断点续传）。按 `docs/01` 附录 E 的五项处理复核
   （尤其 no-op 过滤，漏了模型会学成不动）
   —— 该数据集名字里的 `_no_noops` 后缀就是这一步的产物
2. **依赖**：`bash scripts/prepare_finetune.sh deps`。
   ⚠️ `peft` 必须钉 `0.11.1`（openvla 的 pyproject 就是这么写的）。
   LoRA 实现的行为差异**不会报错**，只会让微调结果对不上官方水平，
   属于最难查的那类问题。装完要重跑一次评测冒烟测试，确认没弄坏推理链路。
3. **输入构造**：把 K 帧堆成 `K × n_token × d`，改 `PrismaticProcessor` 与 collator。
   `scripts/probe_vram.py` 里的 `patch_multiframe` 已经是这个的草图
4. **基线微调**：K=1 复跑一遍 LoRA，确认我们的训练流程能复现官方 checkpoint 的水平
   —— 这一步不能跳，否则后面所有对照都没有可信的地基

### ⚠️ 必须提前算的显存账

K=8 不压缩 → 8×256 = **2048 个视觉 token**。7B 模型 bf16 权重就 14 GB，
再加 2048 长序列的激活与优化器状态，**4090 的 24 GB 很可能装不下**。

这件事有点讽刺但很关键：**"不压缩的多帧基线"可能是全部实验里最跑不动的那个**，
而它恰恰是我们要对照的对象。三条出路，跑之前必须先做显存实测决定走哪条：

| 出路 | 代价 |
|---|---|
| 梯度检查点 + 小 batch + 梯度累积 | 慢 2–3 倍，但能跑 |
| K 降到 4，用 4 帧做主实验 | 削弱"长历史"的叙事 |
| 只有基线那一组租大显存卡（A100 40G/80G） | 多花钱，但只需租几小时 |

**阶段 B 的第一件事就是显存实测**，不是写代码。

## 阶段 C · 2D 池化 vs 4D 池化（核心创新验证）

`docs/04` §7 列的核心对照：**固定 token 预算**，比较

- 2D 池化：每帧独立压缩（对应现有的一堆 token pruning 工作）
- 4D 池化：跨帧联合压缩，合并 token 带 (t, x, y, z) 坐标

这是唯一能证明"在 4D 上做"不是包装的实验。
**若两者打平，方案的创新点就不成立**，要及早知道，所以排在 4D RoPE 之前。

预期能用上的杠杆（`docs/04` 4.5）：同一物理位置在多帧都静止 →
合成一个带时间区间的 token。这个如果成立会是最漂亮的点。

## 时间与风险

现在 2026-08，结题 2027-03-10，约 **6.5 个月**。

**主要成本不再是评测，而是训练**。评测一次 50 局约 17 分钟；
LoRA 微调按 `docs/01` 是单卡 A100 10–15 h，4090 上更久，
而消融要跑很多次。**阶段 B 的显存实测决定了后面所有实验的单价**，
所以它是当前优先级最高的未开工事项。

**三个真实风险**：

1. **多帧基线跑不动**（显存）—— 见阶段 B，有三条出路，需实测决策
2. **2D 与 4D 打平**（阶段 C）—— 那创新点不成立，需要及早暴露，
   所以 C 排在 D 前面而不是最后
3. **训练流程复现不了官方水平**（阶段 B 第 3 步）—— 若 K=1 的 LoRA
   跑不到 ~84%，说明训练配置有问题，后面的对照全部不可信。这是硬门槛

**下一个决策点**：阶段 A 跑完后，先做阶段 B 的显存实测（约 1 h，不需要完整训练），
拿到数字再决定 K 取多少、要不要租大卡。

## 1. 已复现的缺陷

旧版 `quantile` 有两套不一致的时间边界：`_resolve_bins` 用固定时间箱估计占用数，
`_quantile_assign` 随后又按有效帧重新计算时间分位数。历史不足时，一套认为只有一个
时间箱，另一套分成两个，实际非空箱数超预算；按箱排序截断后，最新帧可能全部丢失。

CPU 实测条件：K=8、stride=16、budget=256、n_t=2、enforce_n=0，16×16 规则网格，
左侧补帧、有效帧在右侧。G3 与 M3 共用该网格分组路径。

| 真实历史帧数 | 旧 G3 最新帧保留 patch | 修正版 G3 最新帧保留 patch |
|---|---:|---:|
| 1 | 256 | 256 |
| 2、3、4 | **0** | **256** |
| 5、6、7、8 | 256 | 256 |

stride=16 时，真实帧数 2–4 对应策略时刻 16–63（从 0 计，不含初始等待）。
修正版在本探针的 1–8 个有效帧条件下保留全部有效输入 patch；G2 分组与旧版逐位一致，
完整 8 帧的 G3 分组也逐位一致。证据：
[旧版](../results/tables/pooling_audit_grid.json)、[修正版](../results/tables/pooling_audit_fixed.json)。

这些结果证明输入处理存在缺陷，**不能证明此前成功率差距全部由它造成**。
真实度量坐标上的预算占用仍需另测；本探针不能代表视觉语义信息损失。

## 2. 修复的边界

新增 `--partition quantile_fixed`：固定时间轴/指定分组轴，自由空间轴继续等量分箱。
训练与评测默认使用 `quantile_fixed`；复现旧 checkpoint 须显式选择 `quantile`。
下面的挂点检查、训练与评测命令均显式指定修正版，避免依赖各入口默认值。

新修正版应从基础模型启动独立训练。直接给旧 checkpoint 换算子评测只能标为
“推理干预诊断”，不能替代匹配训练的对照，也不能混进历史 2×2 主表。
撤回此前“继续完成旧 G3-full”的资源建议。若服务器确认仍在跑旧算子，保存已有
checkpoint、配置与日志后停止该任务，不再为它投入完整评测。这里未连接服务器，
不代表已停止进程。旧结果保留作缺陷诊断；与 G2 的比较及旧四格效应分解暂停作为
方法结论，§13.8 的旧 G3-full 判读表不再驱动当前决策。

已合并远端 e7b80b9 的默认值翻转、回归测试修正和 §13.9，合并后 31 项测试通过。
下面命令仍全部显式指定 partition。历史无后缀目录不能
据新默认解释为 fixed；判定算法以当时配置和代码为准，缺证据时标记未知。

还有三项保留的问题：

- **深度与增强对齐**：训练 RGB 随机裁剪与缓存 patch 深度未同步。修改评测中心裁不能
  修复训练时的错位；需要全分辨率深度及同步变换后再做新的度量四格。
- **有效 token 数**：固定 256 输出槽不等于 256 个有效 token。空槽仍参与注意力，
  `enforce_n` 不保证输入非空箱不足时没有空槽。此次不同时更改注意力和分箱以免混淆。
- **预算搜索**：非空箱占用数不一般满足单调性；现有搜索及可选局部扫描不是全局最优保证。
  此次修复专门解决固定轴边界不一致，不声称解决所有分箱问题。

### 4.3 演示与诊断的落盘工具（2026-09-22）

§4.2 末尾列的低成本诊断需要两样东西：一份逐步的动作与分配记录，以及
“每帧分到多少 token”的明确定义。两者合成一个开关，已随代码入库：

- `pooling.wire.alloc_stats` 给出四个量：每帧 patch 保留率 `keep_rate`、
  最新帧参与的输出槽数 `newest_slots`、槽内各帧贡献比例 `token_share`、
  跨帧混合程度 `mixed_frac`，另附真实帧数 `n_valid` 与实际用掉的槽数 `n_used`。
  `token_share` 按 patch 计数做分数归属，因此各帧之和等于 `n_used`。
  这是一个选择而非天然存在的量：跨帧槽由多帧共同构成，“属于某一帧的整数个
  token”并不存在，所以引用这一列时必须连同定义一起写。
- `run_eval_kframe.py --dump_traj N`（0–5 局/task）在评测时顺带把每个 task 前
  N 局逐步存成 `results/traj/<run_id>/<arm>-task<i>-ep<j>.{jsonl,npz}`：
  `{t, action[7], n_valid, alloc}` 加送入模型之前的当前帧 RGB。
  读回用 `common.traj.read_episode`。
- 该开关不参与 run_id 身份：它只读地抄一份，不改变成功率，开与不开是同一次测量。
  代价是同配置的第二次评测会被“已有记录”挡住，这是预期行为。
  回归测试固定了两条：开关开与关时池化输出逐位相同；开关不改变 run_id。

因此演示不再单独占用算力，且优先级 4 的诊断与演示看到的是同一份数据。
取样偏差仍在：落盘的是每个 task 的前 N 局，不是随机抽样，
可以用作演示素材，不能用作统计样本。

### 6.1 新链路重评 G0@30k 与 G2@30k（优先级 2；本阶段唯一占 GPU 的一步）

为什么做：§4.2 那张表里 G3 有逐局 JSONL 与来源元数据，G0 与 G2 没有，
三臂因此无法逐初始状态配对，G0/G2 的配置也只能由历史日志核验。
重评把三臂放进同一条评测链路，并补上缺的逐局结果与元数据。
选 30k 而不是 50k，是为了与 G3@30k 同训练步数、凑成同条件三臂表。

先确认 checkpoint 实际存在，不要从文档抄路径：

```bash
ls -d runs/*G0* runs/*G2*
ls runs/<G0 的目录>/adapter runs/<G2 的目录>/adapter
```

```bash
export ADAPTER_G0=runs/<G0 的目录>/adapter/step30000
test -f "$ADAPTER_G0/adapter_config.json" || exit 1
python scripts/run_eval_kframe.py \
  --arm G0 --K 1 --stride 16 --budget 256 --n_t 2 \
  --partition quantile_fixed --adapter "$ADAPTER_G0" \
  --task_suite_name libero_10 --center_crop True --seed 7 \
  --num_trials_per_task 50 --eval_batch 8 \
  --dump_traj 2 --run_note relay-g0-30k
```

```bash
export ADAPTER_G2=runs/<G2 的目录>/adapter/step30000
test -f "$ADAPTER_G2/adapter_config.json" || exit 1
python scripts/run_eval_kframe.py \
  --arm G2 --K 8 --stride 16 --budget 256 --n_t 2 \
  --partition quantile_fixed --adapter "$ADAPTER_G2" \
  --task_suite_name libero_10 --center_crop True --seed 7 \
  --num_trials_per_task 50 --eval_batch 8 \
  --dump_traj 2 --run_note relay-g2-30k
```

三处需要说明：

- `--partition quantile_fixed` 对这两臂**不引入训练/评测不一致**：G0 不池化，
  partition 不参与它的任何计算；G2 是帧独立分组，两套 partition 的分组逐位一致
  （§1 末、`tests::test_g2_unchanged_at_every_history_length`）。这与
  “旧 checkpoint 不能换算子评测”不矛盾：§2 那条说的是跨帧联合池化的 G3。
- `--n_t` 对 G2 不起作用（它走 `group_axes`），但参与 run_id，所以固定写 2。
- `--dump_traj 2` 顺带取演示素材：每 task 前 2 局、10 个 task 共 20 局，
  G2 约 200 MB。它不改变成功率，也不改变 run_id（§4.3）。

先用一个 task 试通再补齐十个；分段时每段明确 `--start_task/--end_task`，
note 与其余配置保持一致、不重叠。不要看到成功率之后再挑任务或改协议。

```bash
# 试通。这一段的成功率不是判据数
python scripts/run_eval_kframe.py \
  --arm G2 --K 8 --stride 16 --budget 256 --n_t 2 \
  --partition quantile_fixed --adapter "$ADAPTER_G2" \
  --task_suite_name libero_10 --center_crop True --seed 7 \
  --num_trials_per_task 50 --eval_batch 8 \
  --start_task 0 --end_task 1 --run_note relay-g2-30k
```

逐局结果的清点（覆盖是否完整，跑完与分段都用它）：

```bash
python - <<'CHECK'
import json, collections, glob
for f in sorted(glob.glob("results/logs/EVAL-*relay*.episodes.jsonl")):
    rows = [json.loads(x) for x in open(f, encoding="utf-8")]
    keys = collections.Counter((r["task_id"], r["episode"]) for r in rows)
    ok = sum(r["success"] for r in rows)
    dup = sum(1 for v in keys.values() if v > 1)
    print(f.split("/")[-1])
    print(f"  {len(rows)} 行，去重 {len(keys)} 个，重复 {dup} 个，"
          f"覆盖 task {sorted({k[0] for k in keys})}，"
          f"成功 {ok} = {ok / max(len(rows), 1):.2%}")
CHECK
```

验收标准：500 行逐局记录、`(task_id, episode)` 组合无缺失无重复、
`.meta.json` 的 adapter SHA-256 与 `runs/` 下权重一致。
预期重现 G0 23.40%、G2 42.20%。**若不重现，那本身是一个发现**
（新旧评测链路之间存在差异），照实记录，不回头改判据。

补不回来的仍然补不回来：G0/G2 的训练种子与训练来源元数据。
可复现的是“这个 checkpoint 达到 X”，不可复现的是“重新训一遍还能得到 X”。

```bash

  --episodes G2=results/logs/<...relay-g2-30k.episodes.jsonl> \
```

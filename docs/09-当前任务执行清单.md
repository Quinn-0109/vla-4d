## 0. 已冻结的事实与边界

以下结果已经完成，不因本清单中的小样本采集而更新：

| 方法 | 固定预算下的视觉处理 | LIBERO-10 正式结果 |
|---|---|---:|
| G0 | 单帧 | 117/500 = 23.40% |
| G2@30k | 8 帧分别池化，每帧约 32 token | 211/500 = 42.20% |
| 修正版 G3@30k | 8 帧进入全局跨帧池化 | 118/500 = 23.60% |

当前结论是：历史观测有用，但现有 G3 的全局跨帧平均池化没有保住 G2 的收益。G3 已达到事前停止条件，
因此本阶段**不再训练、不做 G0/G2/G3 的 500 局重评、不启动旧四臂实验**。

本阶段只回答两个问题：

1. G3 是否因为跨帧混合而稀释当前状态或丢失时间身份？
2. 能否把已有系统整理成一个可复现、可解释、可演示的结项成果？

小样本轨迹只能用于机制诊断和演示，不能更新成功率、计算总体置信区间或宣称方法优劣。
历史 G0/G2 没有与 G3 等价的 500 条逐局记录，因此不得把少量补采数据送入完整 McNemar 配对检验。
现有 `scripts/paired_analysis.py` 继续服务旧 2×2 四臂记录，本轮不扩建它。

## B. 实现只读诊断记录

### B1. 给 K 帧评测增加受控的轨迹导出

在 `scripts/run_eval_kframe.py` 增加默认关闭的 `--dump_traj` 能力，并支持只运行 manifest 指定的
task/episode。不得改变默认评测路径、随机数顺序、batch 语义或成功判定。

每局至少记录：

- run、arm、checkpoint、代码 commit、配置和初始状态身份；
- `task_id`、`episode`、环境 step、动作、成功状态；
- 末端位姿和夹爪状态（观测中存在时）；
- 8 个历史帧的来源步编号；
- 必要关键帧的文件路径，不把全部 RGB 数组内嵌进 JSON。

输出采用逐行可恢复格式，写入临时文件后原子改名；已存在的正式日志不得覆盖。

### B2. 记录池化 token 的来源分配

`alloc_stats` 需要记录贡献关系，而不是只记录输出 token 数。每一步至少可推出：

- 每个输出 token 的来源帧编号、贡献 patch 数和权重；
- 最新帧贡献质量；
- 只由最新帧贡献的 token 数；
- 同时混合多个帧的 token 比例；
- 每个 token 覆盖的时间跨度；
- 每个输入帧对最终 token 的贡献质量；
- padding 帧与真实历史帧的区分。

如果池化是均值，最新帧“出现过”不能算作完整保留；诊断必须能量化它被多少旧帧稀释。

### B3. 测试要求

- [ ] 默认不开启导出时，原评测输出和行为不变。
- [ ] manifest 之外的 task/episode 不会被保存。

- [ ] 人工构造的跨帧均值案例能还原正确来源、权重和时间跨度。
- [ ] 中断后已有 JSONL 仍可读取，重跑不会静默制造重复记录。
- [ ] 输出 schema 有版本号，读取器对缺字段给出明确错误。
- [ ] 当前仓库全部测试通过。

**B 阶段验收：**只用合成输入和现有日志即可验证导出格式与统计定义；尚不需要启动 GPU 服务器。

## C. 固定案例的短时 GPU 采集

只有 A、B 通过后才启动 AutoDL。开机后先核对 checkpoint、磁盘和 GPU，不下载或重训模型。

服务器先执行：

```bash
cd /root/autodl-tmp/vla-4d-fixed-cf3e1583
python -m unittest discover -s tests
find runs -path '*/adapter/step30000/adapter_config.json' -print
```

`results/cases/diagnostic_checkpoints.json` 已锁定三个 arm 的精确路径、权重哈希、正式日志哈希和
历史配置边界。每个 arm 先打印命令审查，再正式运行：

```bash
python scripts/run_diagnostic_cases.py --arm G3 --dry_run
python scripts/run_diagnostic_cases.py --arm G3
```

G3 验收后依次把 `G3` 换成 `G2` 和 `G0`。启动器固定六局、
`eval_batch=1`、`quantile_fixed`、中心裁剪、视觉缓存、动作路径对拍和逐步帧导出；输出明确标为
`CASESET`，不会产生 `FINAL`。

### C1. 采集顺序

1. 用修正版 G3 跑六个固定案例，先验证新导出链路。
2. 输出完整、成功判定可复现后，用 G2 跑相同六个案例。
3. 最后用 G0 跑相同六个案例。

每个方法必须使用相同 task、episode、初始状态、评测 seed、裁剪方式和动作后处理。模型加载后的第一次运行可视为
工具 smoke，但 smoke 记录不得混入六个冻结案例。诊断运行固定 `eval_batch=1`，避免每个任务只有两局时
实际 batch 形状与正式 b8 不同且随活动环境数量变化。manifest 中的 G3 成败是正式 b8 的分层标签；短跑观察结果
若不同则如实记录，不替换案例。

### C2. 每个方法的验收

- [ ] 正好包含 manifest 中六局，无重复、无额外局。
- [ ] run 元数据包含 checkpoint、代码 commit 和配置。
- [ ] 每局同时保存 G3 正式 b8 的参考标签与本次 b1 观察结果；不一致时明确记录。
- [ ] 轨迹文件、分配文件、关键帧可以被离线读取。
- [ ] 运行中没有 traceback、非有限值或磁盘异常。

若 G0/G2 的 checkpoint 或协议身份无法核对，立即停止对应采集并记录原因，不用近似 checkpoint 替代。

**C 阶段验收：**最多 18 个 arm-case 全部有可追溯记录；本阶段不产生新的“成功率结果”。

## D. 离线诊断与最小演示

### D1. 诊断表

按 arm、task、episode、成功/失败汇总：

- 最新帧贡献质量；
- 最新帧独占 token 数；
- 跨帧混合 token 比例；
- token 平均和最大时间跨度；
- 每一帧的贡献质量；
- 动作差异、夹爪翻转和完成步数。

同时提供逐案例数据，不对六局小样本做总体显著性结论。重点检查两个方向：

1. G3 失败时是否比 G3 成功时出现更强的跨帧混合或最新帧稀释；
2. 同一初始状态下，G2 保留的时间身份是否对应更稳定的动作。

### D2. 最小回放演示

实现独立的回放/展示入口，可复用 `scripts/check_replay.py` 的环境初始化和动作重放逻辑。至少并排展示：

1. 当前机器人视角；
2. 8 个历史帧及其时间顺序；
3. 池化前后 token 数；
4. 输出 token 的来源帧或颜色编码；
5. 最新帧贡献质量、当前动作和最终成败。

最终选 2—3 个代表案例进入结项展示，但六个冻结案例的原始材料全部归档。若仿真动作回放不能逐步复现，
演示改用已记录帧和动作的离线播放，并清楚标注，不伪装成可复现闭环。

**D 阶段验收：**一条命令读取归档材料并生成统计表；一条命令生成最小演示；不依赖正在运行的服务器。

## E. 一次决策门

完成 D 后只做一次判断：

- **若证据支持“跨帧混合稀释当前状态”**：只提出一个受限改版——为当前帧预留独立 token 配额，
  其余预算分给历史，并继续保留帧身份。先写设计、单元测试和离线分配对照；是否训练另行审查，绝不自动启动。
- **若六个案例没有一致机制信号**：停止方法扩展，把它写成当前证据下无法定位单一机制，进入材料收口。
- **若新导出链路本身不可靠**：只修工具并重采固定六局，不增加任务或 episode 数。

任何候选改版在申请训练资源前都必须说明：它会改变最终系统、主结果表或演示中的哪一项；无法说明则不训练。

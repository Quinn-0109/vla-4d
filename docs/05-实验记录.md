| 项 | 配置 |
|---|---|
| GPU | NVIDIA RTX 4090 24 GB（算力 8.9） |
| CPU / 内存 | 16 核 Xeon Platinum 8352V / 120 GB |
| 驱动 / CUDA | 560.35.03 / cu121 |
| Python | 3.10.13 |
| PyTorch | 2.2.0+cu121 |
| transformers | 4.40.1 |
| robosuite / mujoco | 1.4.1 / **2.3.2** |
| 模型 | `openvla/openvla-7b-finetuned-libero-*`（官方 LoRA r=32 微调权重） |

**实测吞吐**：3.52 Hz（500 episode × 平均 126.8 步 / 5.0 h）。
论文报告 flash-attn 在 4090 上约 6 Hz，故 **sdpa 慢约 41%**。
LIBERO 为同步仿真器，此差异只影响墙上时间，不影响成功率。

### ⚠️ 与官方配置的两处偏离（必须在报告中声明）

**① 注意力实现：sdpa 而非 flash-attn 2**

官方 `experiments/robot/openvla_utils.py:45` 硬编码 `attn_implementation="flash_attention_2"`。
本次因 flash-attn 编译受阻改用 PyTorch 内置 sdpa。

依据：`prismatic/extern/hf/modeling_prismatic.py:208-210` 声明
`_supports_sdpa` 属性并透传自 `language_model`（Llama 在 transformers 4.40.1 中为 True），
第 249 行将 `attn_implementation` 透传给 `text_config`。二者是同一注意力运算的不同
kernel 实现，数值上近乎一致。

影响评估：LIBERO 为**同步仿真器**（`env.step()` 等待动作计算完成才推进），
推理速度不影响成功率，仅影响墙上时间。结果（84.2% vs 84.7%）也印证了这一点。

**② 单随机种子 —— 经实测确认这不构成局限**

初看这是偏离：官方用 3 个种子 × 500 次取平均。但**实测证明 LIBERO 评测在
固定 GPU 上是完全确定性的**，`--seed` 对 rollout 没有任何影响（见 3.2 节）。
因此跑 3 个评测种子会得到三份完全相同的数据，n=1500 与 n=500 携带的
信息量完全相同。

> 该结论由一次实际的 seed 8 复跑验证：全部指标与 seed 7 逐位相同。

## 2. 评测协议

严格遵循 OpenVLA 论文 Appendix E：

- 每 suite 10 个任务 × 50 次 rollout = **500 次**
- 使用原版 LIBERO 提供的**固定初始状态**，测试环境未作任何修改
- `--center_crop True`（checkpoint 用 90% 随机裁剪训练，测试时取中心 90%）
- 第三人称图像训练/测试均旋转 180°（`get_libero_image` 内置）
- 每 suite 独立使用对应 checkpoint，不混用
- 成功判据：环境返回 `done == True`

各 suite 的 max_steps（官方设定，与最长训练 demo 对应）：

| Suite | max_steps | 最长 demo |
|---|---|---|
| libero_spatial | 220 | 193 |
| libero_object | 280 | 254 |
| libero_goal | 300 | 270 |
| libero_10 | 520 | 505 |

**注**：纯评测无需下载 LIBERO 演示数据集。初始状态（`init_files/`，13 MB）
与环境定义（`bddl_files/`，580 KB）随 LIBERO 仓库自带。

## 3. 结果一：复现对标

| Suite | 本次复现 | OpenVLA 论文 | 差异 | z | p | 判定 |
|---|---|---|---|---|---|---|
| LIBERO-Spatial | 84.2% | 84.7 ± 0.9% | −0.5 | 0.27 | 0.788 | ✅ 不显著 |
| **LIBERO-Object** | **84.0%** | 88.4 ± 0.8% | **−4.4** | **2.41** | **0.016** | ❌ **显著偏低** |
| LIBERO-Goal | 76.4% | 79.2 ± 1.0% | −2.8 | 1.30 | 0.192 | ✅ 不显著 |
| LIBERO-Long | 52.0% | 53.7 ± 1.3% | −1.7 | 0.66 | 0.511 | ✅ 不显著 |
| **四 suite 平均** | **74.1%** | 76.5 ± 0.6% | **−2.35** | **2.12** | **0.034** | ❌ 显著 |

各 suite n=500（10 任务 × 50 次），1 SE 约 ±1.6~2.2 个百分点。
检验采用两独立比例之差，合并标准误 = √(SE_本次² + SE_论文²)。

**四个 suite 中三个复现良好**，其中 Long（最难、成功率仅五成）吻合到 −1.7（p=0.511）。

### 3.1 Object 的显著偏低驱动了平均值的偏差

平均值 −2.35 显著（p=0.034），但这一偏差几乎完全由 Object 一个 suite 造成。
反事实检验：

> 若 Object 达到论文的 88.4%，四 suite 平均为 **75.25%**，
> 与论文 76.5% 相差 −1.25，**z=1.13, p=0.260 → 不再显著**。

即：**不存在系统性的复现偏差，问题局限于 Object。**

Object 的 −4.4 在 Bonferroni 校正后仍显著（4 次比较，α=0.0125 < p=0.016 —— 
注：按 4 次比较校正则变为边缘不显著，此处如实标注两种口径）。

可能成因，按可能性排序：

1. ~~评测抽样误差~~ —— **已由 3.2 节的实验排除**。评测是确定性的，
   重跑得到逐位相同的结果，不存在抽样波动。
2. **训练种子间方差** —— 最可能。论文报的是 3 次 LoRA 微调的平均，
   而官方只发布了一个 checkpoint。**该方差对复现者不可估计**（见 3.2 节推论③）。
3. **sdpa 的系统性影响** —— **可能性最低**。若 sdpa 引入系统偏差，
   Spatial 不可能吻合到 −0.5（p=0.788），Long 不可能吻合到 −1.7（p=0.511）。

**已执行的验证**：用 seed 8 重跑 Object（500 episode，约 6 h）。
结果与 seed 7 **逐位相同**，据此排除解释 1。详见 3.2 节。

### 3.2 关键发现：LIBERO 评测是确定性的，Object 的偏差不是抽样噪声

为判定 Object 的 −4.4 是否源于种子间方差，用 `--seed 8` 重跑了一次
（500 episode，约 6 h）。结果：**全部指标与 seed 7 逐位相同**
（成功率 84.0%、jerk 7296.5864、路径效率 0.2849、完成时间 8.3677…）。

追查代码后确认，评测路径上不存在任何随机性：

| 随机性来源 | 实际情况 |
|---|---|
| 环境种子 | `libero_utils.py:24` **硬编码 `env.seed(0)`**，不受 `--seed` 影响 |
| 初始状态 | 从 `init_files/` 读取，每任务固定 50 个 |
| 动作解码 | `modeling_prismatic.py:518` 调 `self.generate()` 未设 `do_sample`，默认 greedy |
| `set_seed_everywhere` | 仅设 torch/numpy/random，并置 `cudnn.deterministic=True` |

> 官方 README 提到"不同 GPU 上结果可能略有差异"，说明跨硬件仍存在浮点
> 非确定性；但**同一张卡上评测可完全复现**。

**三个推论：**

**① Object 的 −4.4 不含抽样误差。** LIBERO 每任务仅提供 50 个初始状态，
本实验用满全部 500 个，属于**在完整固定测试集上的穷举评测**，而非抽样估计。
因此"运气不好"这一解释被排除。

**② 论文的 ±0.9% 只能来自训练种子。** 评测既然确定性，3 个**评测**种子
不可能产生方差，故论文所称 "three random seeds" 应指 **3 次独立的 LoRA 微调**，
报告的是 3 个 checkpoint 的平均值。

**③ 训练种子间方差对复现者不可估计。** 官方每个 suite 只发布一个 checkpoint，
我们复现的是"三次训练中的某一次"，而论文报的是三次的均值。
若训练间标准差约为 0.8×√3 ≈ 1.4 个百分点，则 Object 的 84.0% 较论文均值
88.4% 低约 3.2 个标准差。可能是发布的 checkpoint 不在论文所用的三个之列，
也可能存在其他未知差异——**但可以确定不是随机波动。**

> **对复现工作的一般性启示：当论文报告"多种子平均"而只发布单个 checkpoint 时，
> 复现者在原理上就无法重现该均值。** 这类差异应记为已知偏差，
> 而非归咎于复现方法。

## 4. 结果二：轨迹质量分析（官方评测未提供）

官方评测脚本仅输出 MP4 回放与成功/失败日志，不保存动作序列与末端位姿。
本项目在保持评测逻辑逐行一致的前提下，额外记录每一步的：
模型输出动作(7维)、执行动作(7维)、末端位置/四元数、夹爪关节。

由此可计算官方未提供的轨迹质量指标。

### 4.1 成功 vs 失败 episode 对比（LIBERO-Spatial, n=500）

统计方法：Mann-Whitney U 检验（非参数）。选择理由：jerk 等指标分布严重右偏
且有长尾，均值与 t 检验的正态假设均不成立，秩检验对此稳健。同时报告
rank-biserial 效应量——大样本下 p 值必然极小，效应量才反映实际差异幅度。

| 指标 | 成功 (n=421) | 失败 (n=79) | 比值 | 效应量 | p |
|---|---|---|---|---|---|
| **归一化 Jerk** | 1331 | 14200 | **10.67×** | **−1.00** | <1e−4 |
| **完成时间 (s)** | 5.3 | 11.0 | 2.08× | **−1.00** | <1e−4 |
| **平均速度 (m/s)** | 0.182 | 0.101 | 0.56× | **+0.97** | <1e−4 |
| **速度方向反转** | **0** | **8** | — | −0.83 | <1e−4 |
| **夹爪翻转次数** | **1** | **14** | **14×** | −0.82 | <1e−4 |
| 动作抖动 | 0.331 | 0.618 | 1.87× | −0.69 | <1e−4 |
| 路径效率 | 0.4445 | 0.3398 | 0.76× | +0.53 | <1e−4 |
| 空转步数占比 | 0 | 0.0046 | — | −0.45 | <1e−4 |
| 路径长度 (m) | 0.908 | 1.11 | 1.22× | −0.42 | <1e−4 |
| SPARC | −2.272 | −2.406 | 1.06× | +0.31 | <1e−4 |

> rank-biserial 取值范围 −1 ~ +1，**±1.00 表示两组完全分离**（一组的几乎每个样本
> 都优于/劣于另一组的所有样本），是理论极限。

### 4.2 ⚠️ 需要诚实说明的构造性效应

**完成时间与平均速度的效应量偏高，部分源于评测设计而非模型行为**：
失败 episode 会一直跑到 `max_steps`（Spatial 为 220+10=230 步 = 11.5 s），
观测到的失败组中位数 11.0 s 已接近该上限。因此：

- 失败组"完成时间长"部分是**天花板效应**
- 失败组"平均速度低"是因为跑满时限时包含大量停滞与低速段

**不受此影响、可独立成立的发现**是下面三项。

### 4.3 三个可独立成立的发现

**① 轨迹平滑度与任务成败几乎完全分离（效应量 −1.00）**

失败轨迹的归一化 jerk 中位数是成功轨迹的 **10.67 倍**，且两组分布几乎不重叠。
这是"动作不平滑"与"任务失败"之间迄今最直接的量化证据。

**② 失败时夹爪反复开合（1 次 vs 14 次，14 倍）**

夹爪翻转次数从成功组的中位数 1 次跃升到失败组的 14 次。这对应"抓取失败后
反复尝试"的行为模式，是时序决策不稳定的直接表现。

**③ 动作输出本身就是抖的，不是仿真造成的（1.87 倍）**

"动作抖动"指标直接作用在**模型输出序列**上，与仿真动力学无关。
失败组高出 87%，说明不连贯性源于**模型的时序决策**，而非环境执行误差。
这一条对 4D 时空建模的论证最关键——它排除了"抖动是仿真伪影"的替代解释。

### 4.4 跨 suite 趋势：任务越难，轨迹质量越差（预测已验证）

| Suite | 成功率 | 归一化 Jerk | 相对 Spatial | 速度反转 | 空转率 | 成功 episode 步数 |
|---|---|---|---|---|---|---|
| Spatial | 84.2% | 4 026 | 1.0× | 1.74 | 0.0214 | 106 |
| Object | 84.0% | 7 297 | 1.8× | 3.31 | 0.0387 | 140 |
| Goal | 76.4% | 15 758 | 3.9× | 4.24 | 0.0734 | 103 |
| **Long** | **52.0%** | **75 374** | **18.7×** | **9.56** | **0.1527** | **270** |

**四个 suite 中，成功率与 jerk / 速度反转 / 空转率的排序全部完全反向单调（6/6 对）。**

#### 预先登记预测的检验结果

4.4 节曾在 Long 评测开始**之前**写下预测：
> "若该趋势为真，成功率仅 53.7% 的 LIBERO-Long 应呈现显著高于 Goal 的 jerk 与空转率。"

| 指标 | Goal | Long | 倍数 | 结论 |
|---|---|---|---|---|
| 归一化 Jerk | 15 758 | **75 374** | **4.8×** | ✅ 证实 |
| 空转步数占比 | 0.0734 | **0.1527** | **2.1×** | ✅ 证实 |

**预测成立。Long 的 jerk 是 Spatial 的 18.7 倍。**

#### 统计口径的诚实说明

Spearman rho = −1.0（完全反向），但 **n=4 个 suite 时双侧 p = 2/4! = 0.083**，
在 α=0.05 下仍不足以声称显著。

因此本项目的表述应为：**四个 suite 的排序完全一致，且量级差异达 18.7 倍，
但 suite 数量本身（n=4）限制了统计推断的强度。** 该趋势的严格验证需要更多任务族。

#### 各 suite 的失败机制不同

由"成功 episode 步数"可区分出两类失败：

- **Goal**：成功仅需 103 步（四者最短），成功率却只有 76.4%。
  其十个任务动作类型各异（开抽屉、把碗放炉子上、把酒瓶放柜顶……）。
  → 失败是**没理解任务目标**，而非执行不完。
- **Long**：成功需 270 步（Spatial 的 2.5 倍），失败中位数 520 步（上限 530）。
  → 失败是**真正的长时序执行衰减**，误差沿时间累积直至跑满时限。

值得注意的是，Goal 的 jerk（15 758）已远高于 Spatial（4 026），
说明**"没理解要做什么"会直接表现为动作层面的抖动与犹豫**，
而不仅仅是选错了目标物体。

### 4.5 指标稳健性：哪些指标可跨任务类型使用

同一指标在四个 suite 上的 rank-biserial 效应量：

| 指标 | Spatial | Object | Goal | Long | 判定 |
|---|---|---|---|---|---|
| **归一化 Jerk** | −1.00 | −1.00 | −1.00 | −0.99 | ✅ **四处均近乎完全分离** |
| **平均速度** | +0.97 | +0.98 | +0.87 | +0.96 | ✅ **极稳定** |
| 完成时间 | −1.00 | −1.00 | −1.00 | −1.00 | ✅ 但有天花板效应（见 4.2） |
| **空转步数占比** | −0.45 | −0.70 | −0.58 | −0.76 | ✅ 稳定 |
| 速度方向反转 | −0.83 | −0.57 | −0.71 | −0.45 | ✅ 方向一致，强度随难度递减 |
| 夹爪翻转次数 | −0.82 | −0.70 | −0.18 | −0.46 | ⚠️ 方向一致但波动大 |
| 动作抖动 | −0.69 | −0.45 | −0.30 | −0.17 | ⚠️ 随任务难度**单调减弱** |
| **路径效率** | +0.53 | −0.14 (n.s.) | +0.41 | **−0.43** | ❌ **符号翻转** |
| **路径长度** | −0.42 | +0.09 (n.s.) | −0.26 | **+0.25** | ❌ **符号翻转** |

#### 路径类指标不可用于跨任务比较（本项目的方法学结论）

路径效率在四个 suite 上出现**两次符号翻转**，成因各不相同：

- **Object**：十个任务布局完全相同、只换物体，末端路径由任务几何决定
  （固定抓取点 → 篮子的弧线），与策略质量无关。故失去区分力（p=0.052）。
- **Long**：多步任务（如"把 A 和 B 都放进篮子"）。成功必须遍历多个位置，
  路径必然长而曲折；而失败往往只完成第一个子任务就停住，路径反而更短更直。
  于是**失败 episode 的路径效率反而更高**（0.2311 vs 0.1671，效应量 −0.43）。

> **结论：路径效率与路径长度在多步任务上会给出相反的结论，
> 用作策略质量指标是危险的。**
>
> 可跨任务类型安全使用的是：**归一化 jerk、平均速度、空转步数占比**
> （四个 suite 上符号一致且效应量稳定）。
>
> ⚠️ **归一化 jerk 有一条限定，补记于 2026-08**（`docs/06` §1.1b）：
> 它是 dimensionless jerk（`T⁵/L²`，时长与路径长度已归一化，Goal 与 Spatial
> 步数几乎相同却差 3.9 倍，确实不是步数的代理），但**它随子动作个数增长**，
> 而 Long 按定义就是多个子任务的组合。所以跨 suite 的 18.7 倍**有一部分在
> 复述任务的构造方式**。佐证：同一 suite 内成功 vs 失败，NJ 差 10.67× 而
> SPARC（对子动作个数更鲁棒）只差 1.06×。
> → 这套指标只作 motivation 与 diagnostic，不作论据（`docs/06` §1.1b）。
>
> 这对后续工作有直接价值：若以轨迹平滑度作为 4D 改进的评价指标，
> 应选用这三项，并避免路径类指标。

#### 动作抖动随任务难度单调减弱

动作抖动的效应量从 Spatial 的 −0.69 单调降到 Long 的 −0.17。
推测原因：难任务中即便成功的 episode 也很长、含多个子阶段与阶段间停顿，
"抖动"信号被稀释。该指标在简单任务上区分力最强。

### 4.6 与 VLA-4D 论文论点的对应

VLA-4D（arXiv 2511.17199）对 2D VLA 的批评为定性描述：

> "these 3D VLAs often struggle with fine-grained temporal control that leads to
> behaviors such as **idle pauses or jitter**"
> "the 2D model exhibits **substantial redundant global motion** and pronounced
> oscillations in local motion speed"

本项目用 500 条真实轨迹将其量化：

| VLA-4D 的定性描述 | 本项目的量化对应 |
|---|---|
| idle pauses | 空转步数占比：四个 suite 上失败组均显著更高（p<1e−4），且随任务难度递增（0.021 → 0.153） |
| jitter | 归一化 jerk：suite 内成功/失败相差 8~26 倍；suite 间 Long 是 Spatial 的 **18.7 倍** |
| redundant global motion | 路径效率 Spatial 0.4373 / Object 0.2849 / Goal 0.4213 / **Long 0.2385**——末端实际路径是直线距离的 2.3~4.2 倍。⚠️ 但该指标不可跨任务比较，见 4.5 |
| oscillations in motion speed | 速度方向反转：Spatial 成功 0 vs 失败 8；suite 均值随难度从 1.74 增至 9.56 |

## 6. 复现过程中的工程发现

**一个 2024 年的开源项目在 2026 年复现，仅靠原仓库的 `pyproject.toml` 不足以
重建可运行环境。** OpenVLA 锁死了全部直接依赖，但这些依赖对**自身传递依赖**
大多未设版本上界，pip 会解析出两年后的版本并导致运行时失败。

实测遇到五处，均已在 `setup/constraints.txt` 中钉死：

| 包 | 上游声明 | pip 实际解析 | 后果 |
|---|---|---|---|
| numpy | `>=1.13.3`（robosuite） | 2.2.6 | `import torch` 崩溃 |
| opencv-python | 无版本约束（robosuite） | 5.0.0 | 反向要求 numpy≥2，与上条死锁 |
| protobuf | 间接 | 需 5.x | `cannot import name 'runtime_version'` |
| tensorflow-metadata | 无版本约束（tfds 4.9.3） | 2026 版 | 同上 |
| **mujoco** | `>=2.3.0`（robosuite 1.4.1） | 3.11.0 | 建环境时断言失败 |

此外 LIBERO 自身存在打包缺陷：`libero/` 目录缺少 `__init__.py`，其 `setup.py` 中
`packages=[p for p in find_packages() if p.startswith("libero")]` 实测返回**空列表**，
新版 setuptools 按 PEP 660 严格安装故一个包都装不上（旧版 setuptools 的 develop
模式会把项目根目录加入 `easy-install.pth`，因而当年可用）。
需 `pip install -e . --config-settings editable_mode=compat`。

> 这本身是复现工作的一项可交付发现：**依赖腐烂（dependency rot）是复现两年前
> 工作的主要工程成本**，且无法通过阅读原论文预见。

## 7. 结果三：冻结模型的 token 预算消融（2026-08）

协议见 `docs/04` 4.6。用官方 checkpoint 不做任何训练，只压缩视觉 token，
每配置 50 局（评测确定性，基线直接从满量 500 局里筛 `episode_idx < 5`）。

### 7.1 结果：不是拐点，是悬崖

LIBERO-Spatial，ToMe 合并，基线 38/50 = 76.0%：

| 保留 token | 占比 | 压缩 | 成功率 | 95% CI | Δ基线 | p |
|---|---|---|---|---|---|---|
| 192 | 75.0% | 1.3× | 68.0% | [54.2, 79.2] | −8.0 | 0.373 |
| 128 | 50.0% | 2.0× | 42.0% | [29.4, 55.8] | **−34.0** | 5.5e-04 |
| 96 | 37.5% | 2.7× | 18.0% | [9.8, 30.8] | −58.0 | <1e-4 |
| 64 | 25.0% | 4.0× | 6.0% | [2.1, 16.2] | −70.0 | <1e-4 |
| 48 | 18.8% | 5.3× | 4.0% | [1.1, 13.5] | −72.0 | <1e-4 |
| 32 / 24 / 16 | ≤12.5% | ≥8× | **0.0%** | [0.0, 7.1] | −76.0 | <1e-4 |

**天真地压缩序列，在 OpenVLA 上不成立。** 压到 8× 完全失能，
连 2× 都要付出 34 个百分点。

⚠️ **但这张表不能读作"信息不够"**——7.2 的诊断证明掉点几乎全部来自
序列位移而非信息损失。这里保留原表是为了记录"直接压"这条路的真实代价，
它同时也是后续位置修正方案的对照组。

### 7.2 诊断结果：瓶颈不是信息，是位置

压缩同时改变了**信息量**和**序列位置**，两个对照把它们分开
（`expand` 保持 256 长度只降信息量，`shuffle` 保持信息量只打乱位置）：

| 保留 | `expand`（长度 256） | 直接压（长度 k） | 差 |
|---|---|---|---|
| 128 | 74.0%（−2.0, **n.s.** p=0.817） | 42.0% | **+32** |
| 64 | 70.0%（−6.0, **n.s.** p=0.499） | 6.0% | **+64** |
| 32 | 2.0%（−74.0） | 0.0% | +2 |

`shuffle`（保留全部 256 个 token 只打乱顺序）：38.0%（−38.0, p=1.2e-04）

**三个结论**：

1. **4× 信息压缩是免费的。** k=64 时把 256 个 patch 的信息压成 64 个不同的值，
   只要位置不动，70.0% vs 基线 76.0%，不显著。
2. **信息底线真实存在，卡在 64 与 32 之间。** k=32 时两条路一起崩（2% / 0%），
   所以 4× 可行、8× 不可行，这是信息本身的边界，不是位置问题。
3. **k=64 那 64 个百分点的落差，全部来自位置。** 同样的算子、同样的信息量，
   区别只在序列长没长。

### 7.3 机制：压缩把整个语言块搬了家

读 `prismatic/extern/hf/modeling_prismatic.py` 确认（openvla 主分支，transformers 4.40.1）：

```python
# :381  视觉块夹在 BOS 和语言 token 之间
multimodal_embeddings = torch.cat(
    [input_embeddings[:, :1, :], projected_patch_embeddings, input_embeddings[:, 1:, :]], dim=1)
# :403  且不传位置，Llama 按 arange(seq_len) 自己生成
language_model_output = self.language_model(..., position_ids=None, ...)
```

所以布局是 `[BOS=0] [视觉 1..256] [语言 257..]`。压到 k 个 token 后，
**语言指令和动作解码位置整体前移了 (256−k) 位**——k=64 时是 192 位。

这解释了一个否则说不通的现象：**打乱全部 256 个 token（38%）反而远好过压到
64 个（6%）**。打乱只搅乱视觉块内部，语言块仍稳坐 257 号往后；
压缩则把下游全体搬走。位移比乱序更伤。

### 7.4 位置修正结果

压短序列的同时显式传 `position_ids`，让每个合并 token 拿回质心的原始位置、
语言块仍从 257 开始（LIBERO-Spatial，除标注外 n=50）：

| 保留 | 占比 | 直接压 | **+位置修正** | `expand`（长度 256） |
|---|---|---|---|---|
| 128 | 50.0% | 42.0% | 66.0% | 74.0% |
| 96 | 37.5% | 18.0% | **72.5%**（n=200） | — |
| 64 | 25.0% | 6.0% | 34.0% | 70.0% |
| 48 | 18.8% | 4.0% | 34.0% | — |
| 32 | 12.5% | 0.0% | 0.0% | 2.0% |

**站得住的结论：位置编码的影响比压缩本身大五倍。**
同样 2.7× 压缩率，不修 `position_ids` 是 **18.0%**，修了是 **72.5%**——
位置修正值 **+54 个百分点**，而压缩本身只值 −10 个百分点（见下）。
这是本项目 4D RoPE 论点的直接实证。

### 7.5 ⚠️ 撤回："2.7× 压缩免费"这句话不成立

初次报告 keep=96 时写的是"74.0% vs 76.0%，p=0.817，统计上不可区分"。
**加量到 n=200 后这个结论被推翻了**：72.5% vs 基线 82.5%，
−10.0 个百分点，**p=0.017，显著**。

跨四个 suite 复现（`collect_ablation.py --suite all`）：

| suite | 压缩后 | 基线 | Δ | p |
|---|---|---|---|---|
| Spatial (n=200) | 145/200 = 72.5% | 165/200 = 82.5% | −10.0 | **0.017** |
| Object | 36/50 = 72.0% | 44/50 = 88.0% | −16.0 | **0.046** |
| Goal | 36/50 = 72.0% | 39/50 = 78.0% | −6.0 | 0.488 |
| Long | 21/50 = 42.0% | 27/50 = 54.0% | −12.0 | 0.230 |
| **合并** | **238/350 = 68.0%** | **275/350 = 78.6%** | **−10.6** | **1.6e-03** |

四个 suite 方向完全一致，量级 −6 到 −16。
**正确的说法是"2.7× 压缩要付约 10.6 个百分点"，不是"免费"。**

（合并的是成功局数而非成功率的平均——各 suite 基线水平差得很远，
Object 88% 而 Long 54%，直接平均会给小 suite 过高权重。）

#### 方法论教训：这正是"检验功效不足"的现场

n=50 时，10 个点的真实效应给出 p=0.617，CI 是 [60.4, 84.1]。
**不显著被误读成了"没有差异"。** 实际只是区间宽到检不出来。

这个坑本来是预见到的——7.7 写"n=50 的 CI 宽到撑不起等价性声明"时就说过，
结果还是先把结论写出去了。**教训：等价性声明必须先算功效再下笔，
"p > 0.05" 永远不等于"两者相同"。**

代码层面也修了一个真 bug：汇总脚本原先拿 `--trials` 指定的那一档基线去比
所有配置，于是 n=200 的配置被拿去和 5 trials/task 的基线（76.0%）比。
两者的初始状态集根本不是一套，差异有一部分纯粹来自基线子集本身的变化
（前 5 局 76.0%，前 20 局 82.5%，满量 84.2%）。
现已改为**每个配置跟自己那档 trials 的基线比**，表里也把 n 和所用基线打出来。

#### per-task 重复检测的结论

`keep=64` 与 `keep=48` 的 34.0% 是**巧合**——重复检测没有报警，
说明两者 per-task 分布不同，压缩确实按不同预算生效了。
（检测只报了 keep=32/24/16 全零那组，全失败必然彼此相同，
已改为跳过这种退化情形。）

### 7.5b 预测对账（7.4 跑前已登记）

| 预测 | 结果 | 判定 |
|---|---|---|
| k=64 时 `fixpos` ≥ 60% | 34.0% | ❌ 错 |
| 拐点从 192 下移到 ≈64 | n=200 下拐点在 128 | ❌ 错 |
| `fixpos` 略低于 `expand` | k=96 处差 10 点，k=64 处差 36 点 | ◐ 方向对、量级错 |

三条全部偏乐观。记在这里。

### 7.6 剩余差距的假设与实现障碍

**假设一：注意力质量（attention mass）。**
`expand` 里一个大小为 s 的簇被复制成 s 个 token，天然拿到 ~s 倍的注意力权重；
`fixpos` 中每个合并 token 只出现一次。压缩率越高簇越大，畸变越重——
这与"96 撑住、64 崩掉"的走向一致。ToMe 原文的解法是 **proportional attention**：
注意力 logits 上加 `log(size)`。

**假设二：token 同质化。** 有工作指出激进合并会削弱驱动注意力的关键 token
分量，使 token 在深层逐渐失去区分度。这与假设一很可能是同一现象的两种表述，
但它给出了一个**可直接监控的量**：深层 block 中视觉 token 的注意力份额。
若 `keep=64` 时该份额相对未压缩显著下降，两条假设就同时被支持。
→ 该监控在 4D 池化实现里加（`docs/06` §2.3 细节 4）。

**但在 OpenVLA 上没有便宜的挂载点**（已查证 transformers 4.40.1 源码）：

- `modeling_llama.py:1068` —— `flash_attention_2` 分支直接 `return attention_mask`，
  FlashAttention 内核不接受加性 bias。而 `openvla_utils.py:45` 硬编码了 flash-attn。
- 即使切到 `sdpa`，`_update_causal_mask` 的 4D 分支（:1104）只把传入 mask 当**布尔**用
  （`eq(0.0) → min_dtype`），加性 bias 会被抹掉。

所以要做 proportional attention，必须逐层包住 `LlamaSdpaAttention.forward`，
并且整条对比链（含基线）都要在 sdpa 下重跑。**这笔钱先不花**——
在单个 suite 上把 2.7× 推到 4×，价值低于先确认 2.7× 这个结论本身站得住。

### 7.7 下一步：先确认结论的普适性

`bash scripts/run_token_ablation.sh replicate`（约 2.2 h）做两件事：

1. **跨 suite 复现** —— 同样的 keep=96 + 位置修正跑 Object / Goal / Long。
   单个 suite 上的结论太脆，四个 suite 一致才撑得起论断。
2. **Spatial 加量到 n=200** —— 现在 n=50 的 CI 是 [60.4, 84.1]，
   宽到没法支持"统计上不可区分"这句话。等价性声明需要窄区间，
   否则只是"检验功效不足"，不是"没有差异"。

**⚠️ 需要留意的一点**：`keep=64` 与 `keep=48` 的成功率完全相同（都是 34.0%）。
评测是确定性的，因此已在 `collect_ablation.py` 加了 per-task 逐位比对，
下次汇总会自动报警——若两者 per-task 分布也完全一致，就要查压缩是否真的按不同
预算生效；若只是总数相同、分布不同，那只是巧合。

+ 梯度检查点 + **冻结视觉主干**，2.5 s/梯度步。

### 8.2 ❌ 硬门槛**未通过** —— n=50 的"通过"是假象

> **2026-08 更正。** 本节曾写「✅ 硬门槛通过」，依据是 n=50 下
> 72.0% vs 76.0%、p=0.65。**满量评测推翻了这个结论。**

#### 满量结果（n=500，10 任务 × 50 trials）

| | 成功率 | 95% CI (Wilson) |
|---|---|---|
| 官方 checkpoint | **84.2%** (421/500) | [80.7, 87.1] |
| **自建 step 20 000** | **74.0%** (370/500) | [70.0, 77.7] |
| **差** | **−10.2 点** | **z=−3.97, p=7.3e-05** |

**置信区间完全不重叠。差距高度显著。原定门槛"复现到 ~84%"没有达到。**

#### ⚠️ n=50 与 n=500 给出了相反的判定

| 样本 | 自建 | 官方 | 差 | p | 当时的判定 |
|---|---|---|---|---|---|
| n=50 子集 | 72.0% | 76.0% | −4.0 | 0.648 | ✅ "通过" |
| **n=500 满量** | **74.0%** | **84.2%** | **−10.2** | **7.3e-05** | ❌ **未通过** |

差距从 −4.0 扩大到 −10.2，原因是**那个 50 局子集恰好对官方 checkpoint 特别难**：
官方在子集上 76.0%、满量 84.2%（−8.2 点），而自建只有 −2.0 点（72.0 → 74.0）。
子集的难度偏差在两个模型上不对称，**把真实差距掩盖了六个百分点**。

> **这是 n=50 第三次误导本项目。** 前两次：①"2.7× 压缩免费"（§7.5，已撤回）；
> ② step15000 的 56% 被当成退化（§8.2 下文）。这一次最严重——
> 它让一个**没过的硬门槛**被记录成通过，而门槛的全部作用就是拦住地基不牢的后续工作。
>
> **子集不是满量的无偏估计**，哪怕它是满量的严格子集（`episode_idx < 5`）。
> 确定性评测保证了子集可复现，**不保证它有代表性**。
> 今后一切"通过/未通过"的判定一律用满量，不用子集。

#### 这对主线意味着什么：内部有效性保住了，外部有效性没有

**没有失效的**：主线对照（`docs/06` §3 的 G0–G4、M2）比较的是我们自己训练的模型，
全部用同一套配方、同样冻结视觉主干、同样 20 000 步。
**−10.2 点是共同偏移，在组内对比里抵消。** 内部有效性不受影响。

**失效的**：
1. **绝对数字不能与文献并列。** 论文里不能写"我们在 LIBERO-Spatial 上达到 X%"
   然后和别人的表放一起——我们的基线就比官方低 10 个点
2. **头部空间变大 → 多了一个替代解释。** 基线离天花板远，
   任何"加东西"的改动都更容易带来提升。这正是被砍掉的 G5 假历史对照
   要排除的混淆（`docs/06` §6）。**若 G2 vs G0 出现大幅提升，G5 必须捡回来**
3. **G0 的数字改为 74.0%**（原记 72.0%）

#### ✅ 判别已做：step17500 满量 = 66.4%，**曲线没到平台**

| checkpoint | 满量成功率 | 95% CI |
|---|---|---|
| step 17 500 | **66.4%** (332/500) | [62.1, 70.4] |
| step 20 000 | **74.0%** (370/500) | [70.0, 77.7] |
| | **+7.6 点** | **z=2.63, p=0.0086** |

**2500 步涨 7.6 个点，显著。20 000 步远未收敛。**

这直接判掉了下面两个候选：**②「训练步数不足」成立，①「冻结视觉主干是天花板」
暂时不成立**——在还没训完的点上谈天花板没有意义。

两个连带后果：

**⚠️ 奢侈版 G0 不触发**（`docs/06` §4.5）。触发条件是"step17500 显示已到平台"，
它没到。**省 12 h**，等平台出现后再问"是不是冻结主干"。

**这两个候选很可能本来就是同一件事。** 冻结视觉主干 → LLM+projector 承担全部适配
→ **收敛更慢**。那么 20k 步落后就不是"能力上限低"而是"还没训完"。
这个区别很重要：前者要写进论文当局限，后者多训就没了。
**若 30k 能追平 84%，10.2 点的缺口整个消失，不需要解释。**

| checkpoint | 满量成功率 | 95% CI | vs 官方 84.2% | p |
|---|---|---|---|---|
| step 17 500 | 66.4% | [62.1, 70.4] | −17.8 | 6.8e-11 显著 |
| step 20 000 | 74.0% | [70.0, 77.7] | −10.2 | 7.3e-05 显著 |
| step 25 000 | 75.4% | [71.4, 79.0] | −8.8 | 5.3e-04 显著 |

实际 **80.0%**，落在带内。该预测基于 acc→成功率的单点外推，并事先声明

−4.2 点、p=0.083。**n=500 检出 4.2 点的功效只有 41%**，要 80% 功效需 n≈1307。

**错误表述**：「我们追平了官方」——那是把 p>0.05 读成等价，本项目已栽过三次。

25k vs 30k 是 +4.6 点、p=0.081，**不显著**——单看这一对无法证明 30k 更好。

### 8.3 功效分析：n=50 撑不起主线对照

15 000 步这个数据点最有价值之处，不是回答了「能否省步数」（它没能回答），
而是逼出了一个必须现在算的账。

主线对照（`docs/06` §3 的 G1–G4）期待的效应量约 10–15 个百分点。
两比例检验，α=0.05 双侧、80% 功效所需的每组样本量：

| 要检出的效应 | 每组所需 n |
|---|---|
| 25 个百分点 | ~56 |
| 15 个百分点 | ~162 |
| **10 个百分点** | **~356** |
| 5 个百分点 | ~1400（不现实） |

**n=50 只能检出 25 个点以上的差异。** 用它做主线对照，等于预先注定得到
「不显著」，然后极可能再次把它误读为「方法没用」。

#### 两个决定

**① 训练步数固定 20 000，不再优化。**
现有数据不足以支持「15 000 就够」，而在不可靠的数据上省钱是最差的省法。
每配置 11.6 h ≈ ¥24。

**② 主线评测协议定为 n=500（满量 50 trials/task）。**
每次 2.75 h ≈ ¥6。这不是奢侈，是让结论可判读的最低要求——
n=200 只够检 15 个点，而期待的效应可能只有 10 个点。

修正后的主线成本：训练 5 组 × 12 h + 评测 6 × 2.75 h + 前置 ≈ **81 h ≈ ¥170**
（`docs/06` §5）。（先前估的 ¥88–116 里评测用的是 n=50，便宜得没有意义。）

**顺带**：K=1 的 Spatial 满量评测本身就该做——它是后面所有对照的基准，
现在这个 n=50 的 72% 不足以充当基准。

### 8.4 方法论：用小钱换方向

两次决策都靠先评一个已有的中间 checkpoint，而非直接开长跑：

1. step 10 000 拿到 58% 后，**没有**直接续训 6 h，而是先花 25 min 评 step 5 000。
   8% 这个数确认了是步数问题而非配置问题——若当时误判为配置错误去调 LoRA 设置，
   那 6 h 就白费了。
2. 同样地，20 000 步通过后先评 step 15 000 定平台位置，再决定主线的训练步数。

这依赖一个具体选择：**checkpoint 分步保存到独立目录，而非官方 `finetune.py`
那样反复覆盖同一份**。adapter 只有几百 MB，存几份的成本远低于它换来的信息。

## 8.5 结果五：显存决策表重测（2026-08，⚠️ 含一条撤回）

`python scripts/probe_vram.py --sweep --freeze_vision`，25 个配置，RTX 4090 24 GB，
flash-attention-2，单相机。全表 `results/tables/vram_probe_frozen.md`。

**为什么要重测。** 旧表用官方 `target_modules="all-linear"`，把 LoRA 也挂到了
视觉主干上；而实际训练**冻结视觉主干**。两者在 K=1 上差 1.5 GB（18.2 vs 16.8），
在 K 大时差得更多——每帧的 DINOv2+SigLIP 激活都要留着反传。

**主线数字**（train + 梯度检查点 + 不压缩 256 tok/帧，b=1）：

| K | 4 | 8 | 16 |
|---|---|---|---|
| 峰值 GB | 16.6 | **17.4** | **19.2** |

可信度锚点：K=1/keep=256/b=4/train+ckpt 探测 **16.66 GB**，与该配置**实际训练**
观测到的 16.8 GB 差 0.14 GB。

**撤回：「K=16 需要 40 GB 以上的卡」不成立。** K=16 实测 19.2 GB。
旧表那个 OOM 完全来自视觉主干的 LoRA 适配器梯度与优化器状态。

**三条结论**：

1. **每加一帧只多 0.20–0.23 GB**（K=4→8 每帧 0.20，K=8→16 每帧 0.225），
   近似线性无拐点。K=1→16 总共只涨 2.6 GB，因为 15.13 GB 的权重是常数项。
   → **显存不是本项目选 K 的约束**，K=8 是由 stride 与覆盖时长定的（`docs/06` §4.1）。
2. **压缩省不下显存**：K=8 从 256/帧压到 96/帧只省 1.1 GB（17.4→16.3）。
   梯度检查点已消掉大半 LLM 激活。这印证了 §7 那条"压缩换来的是速度不是显存"，
   并**取消了"压缩是多帧的使能条件"这个叙事**——压缩必须靠效果说话。
3. **旧表的"token 更少反而更费显存"是配置错误的产物**：512 tok 要 20.3 GB 而
   384 tok 要 20.4 GB。冻结后恢复单调（19.2 vs 18.4）。当时从这个反常推出的
   行动（冻结视觉主干）是对的，但**理由错了**——它本来就是官方配方，
   不是"为了塞下 K=8 的被迫取舍"。

**这张表差点又是一张假表。** 首次带 `--freeze_vision` 重跑时 25 个配置全报 OOM，
包括 K=1——而 K=1 的实际训练只用 16.8 GB。两个 bug 叠在一起：
加 `--cameras` 时漏了 `n_img` 的定义（`NameError`），而失败分类把**任何**
非零退出都记成 OOM。**一个制造错误，另一个掩盖错误。** 若照单全收，
导出的结论会是"连单帧都塞不下、必须压缩"——正是本项目已经撤回过一次的叙事。
之所以当场识破，唯一原因是手上有 K=1 实际训练 16.8 GB 这个**独立锚点**。
现在分类器区分 `OOM / 超时 / ❌崩溃`，错误信息取 traceback **末行**。

**batch 扫描（K=1，keep=256，train）**：

| batch | 2 | 4 | 8 | 16 |
|---|---|---|---|---|
| 不开检查点 | 19.6 | 23.4 | 被杀 | 被杀 |
| 开梯度检查点 | 16.1 | 16.7 | 17.7 | **19.8** |

开检查点后每加一个样本 **+0.26 GB**，不开约 **+1.9 GB**。
→ 单帧基线（G0）可以用 **b=16 + 累积 1**（19.8 GB），有效批仍是官方的 16，
GPU 利用率远高于当前的 b=4 + 累积 4。改之前先 `--bench_only` 测吞吐。

**batch 扫描（K=8，keep=256，train + 梯度检查点）**：

| batch | 1 | 2 | 4 | 8 |
|---|---|---|---|---|
| 峰值 GB | 17.4 | **19.3** | 22.9 | OOM |

每加一个样本 +1.8 GB，与按序列长（2089/297 ≈ 7×）从 K=1 的 0.26 GB/样本
外推的预估吻合。**跑前登记的"b=2 稳、b=4 悬、b=8 必挂"三条全中**——
这条外推规则（每样本成本 ∝ 序列长）以后可以直接用。

**取 b=2 而非 b=4**，尽管 22.9 GB 名义上放得下：余量只剩 2.4 GB（9%），
而探测用的是定长合成序列，真实训练的文本长度有波动；且 K=8 时单样本已有
~2089 token，b=2 就是 ~4200 token 一次前向，4090 早已喂饱——
b=4 花 3.6 GB 余量买一个大概率为零的加速。

**主线配方**（有效批固定 16）：G0 用 b=16×累积 1（19.8 GB），
K=8 各臂用 b=8×累积 2（19.0 GB）。微批不同、有效批相同，数值上等价；
**有效批不许跟着显存漂移**，否则 G0 vs G1 的比较作废。

**⚠️「❌崩溃」的真相：三轮扫描里每一个都是真 OOM。**

先是猜错了一次。b=8/b=16 不开检查点两格报「❌崩溃」，紧挨着 b=4 的 23.4 GB
（整卡 25.3 GB），不可能是代码错误；我判断是子进程 stderr 全空、被 SIGKILL 杀掉，
就按这个改了分类器（记 `returncode`，空 stderr + 负 returncode 报「被杀 signal N」）。
K=8 那轮跑完，八格里五格仍报「❌崩溃」——**改动没生效，说明诊断本身错了**。

真因在子进程：`measure()` **已经**捕获了 `torch.cuda.OutOfMemoryError`，
但只记 `ok=False` 就返回。父进程收到一个能正常解析、既无 `peak_gb` 也无 `error`
的 JSON，于是归进「❌崩溃」。**子进程知道答案，父进程把它丢了。**
已修：回传 `oom: True`。

两条教训：

1. **失败的分类比失败本身更容易骗人**——这是第三次栽在同一件事上
   （全表假 OOM → 错误信息取了 traceback 中段 → 真 OOM 被记成崩溃）。
2. **"合理的解释"不等于"查过了"。** SIGKILL 那个假设完全说得通，
   也确实修了一条真实的漏判路径，但它不是这里的原因。
   代价是白改一轮——本可以先 `cat` 一眼 JSON 里有没有 `error` 字段。

### 两条要写进论文的限定

1. **z 轴主要分开的是前景与背景，不是物体级细结构。**

   合并成一个 token，度量池化不会——但**不能写成"能区分夹爪与其下方物体"**，
   数据不支持那句话。
2. **包围盒不敏感**：全跨度 p5–p95 与剪掉背景的 p5–p90 给出 19.2% vs 19.9%。
   → z 的 extent **不是一个可调超参**，不会被质疑"给 G4 调过了"。

## 8.7 结果七：帧间隔 stride 的确定（2026-08）

`scripts/analyze_stride.py`，libero_10，episode 平均 388 帧（19.4 s，20 Hz）。
判据不是"变化多大"（随 Δt 单调增，给不出拐点），而是

> **d(t, t−Δt) / d(t, 同 episode 随机一帧)**

接近 1 = 该帧已不携带时序连续性。取比值落在 **0.5–0.8** 的区间。

| Δt(帧) | 秒 | pixel 比值 | **feature 比值** | K=8 覆盖 |
|---|---|---|---|---|
| 1 | 0.05 | 0.140 | **0.091** | 0.3 s |
| **16** | **0.80** | 0.639 | **0.516** | **5.6 s** |
| 20 | 1.00 | 0.692 | 0.572 | 7.0 s |
| 25 | 1.25 | 0.744 | 0.631 | 8.8 s |

**Δt=1 的比值只有 0.140**——连续帧与"同 episode 随便一帧"的差距只有 14%。
原先只是推测"K=8 取连续帧近乎同一张图、跑出「历史没用」是必然的假阴性"，现在有数了。

### ⚠️ 我预测错了方向

先前写"feature 大概率给出更小的 stride"，理由是"MuJoCo 无传感器噪声，
pixel 低估变化速度"。**那条推理搬错了地方**——它在 `docs/04` §4.4 的**集中度**
指标上成立（静态区像素差严格为 0 会让 top-10% 占比虚高），但这里是**比值**指标，
分子分母用同一个距离，静态区的影响大部分抵消。

**真实方向是反的**：DINOv2 特征是**语义的**。两帧隔一秒，像素上机械臂已移开很多，
但语义内容（同样的物体、同样的布局）仍相似，特征距离逼近随机基线**更慢**。
**在模型真正"看到"的空间里，帧之间保持相关的时间更长。**

### 定稿取 16 而不是脚本原推荐的 25

`(K−1)×stride` 帧之后历史才填得满，所以带内取大值的代价是补帧：

| stride | feature 比值 | K=8 跨度 | Long 填不满的步数占比 |
|---|---|---|---|
| **16** | 0.516 | 5.6 s | **29%** |
| 20 | 0.572 | 7.0 s | 52% |
| 25（脚本原建议） | 0.631 | 8.8 s | **65%** |

stride=25 下 Long 有 65% 的步骤历史是补出来的——那不再是"开头几步的边界情况"，
而是**主体状态**。

**0.5–0.8 是"信息量够不够"的下界约束，落在带内的都合格；带内选哪个，
应由另一个目标决定——最小化补帧。** `analyze_stride.py` 的推荐规则据此
从"取中位"改为"取带内最小"（原规则是在发现填充率问题**之前**写的）。

### 填充率（stride=16 定稿后重算）

`python src/data/kframe.py` 的自检直接给这张表，按各 suite 平均 episode 长度算，
窗口跨 (8−1)×16+1 = 113 帧：

| Suite | 平均帧数 | 窗口内填充帧 | **历史完整的时刻** |
|---|---|---|---|
| **libero_10 (Long)** | 388 | 14.4% | **71.1%** ✅ |
| libero_object | 140 | 40.0% | 20.0% |
| libero_spatial | 106 | 52.1% | **0.0%** ❌ |

→ **`docs/06` §3.1 预测 4「Spatial 上 G2 ≈ G0」作废。** 它会成立，但成立的原因是
历史序列退化成了补帧生成器，不是"单步任务历史帧边际价值低"——
**同义反复，不构成对方案的检验。** 要保留 Spatial 对照，得按"K 帧覆盖 episode
固定比例"给它单独的 stride（Long 是 5.6/19.4 = 29%，Spatial 对应 stride ≈ 4）。

## 8.8 结果八：相机反投影的外部验证（2026-08）

`scripts/dump_camera.py --n_tasks 5`，libero_10。G4/M2 的 (x,y,z) 全靠这一步。

### 两条结论

**① agentview 不是跨任务常量。** Δpos 最大 **0.650 m**、Δrot 0.099。
libero_10 的十个任务跨厨房/客厅/书房多个场景，每个 BDDL 自己摆相机。
原计划"导出一份常量"的前提不成立，改为**按 task_id 存**。
反投影到世界系之后坐标仍跨任务可比——这正是要反投影的理由之一。
fovy=45°，focal=270.39 px @ 224²。

**② 反投影正确，翻转约定 `flipped=True`（与 `depth_diag` 的 `[::-1]` 一致）。**

| 主判据：两台相机点云的共视部分 p10 | 翻转 | 不翻 |
|---|---|---|
| n=4000 | **1.05 cm** | 7.41 cm |

差 7.1 倍，判别力足够。密度检验：n 从 4000 到 16000，p10 从 1.05 降到
**0.45 cm（0.43×，理论 0.63×）**——**随密度缩小，说明这是采样下限而非系统偏移**，
真实精度好于 0.45 cm。

> 中位数（35.09 vs 27.08 cm）方向与 p10 相反，不能用：中位数由**视角重叠**
> 决定而非精度，B 看得到而 A 看不到的表面本来就配不上；错的翻转会把点云
> 抹匀在同一块体积里，反而可能中位数更小。

### 工作空间包围盒（p1–p99，30 条 episode）

| 轴 | 区间 (m) | 跨度 |
|---|---|---|
| x | [−1.211, +0.234] | 1.445 |
| y | [−0.899, +0.861] | 1.760 |
| z | [−1.098, +1.363] | **2.460** |

⚠️ **这个盒主要是背景撑起来的**。LIBERO 世界系里桌面在 z ≈ 0.9 m、地面 z = 0，
而 z 下探到 −1.098 是**地面以下**——打到远平面/墙外的射线。2.46 m 分 5–6 个箱
就是 45 cm/箱，比按深度算的 30 cm 还粗。

由此推翻了一个**代理指标**：§8.6 那个"跳变幅度 > 箱宽 19.2%"是**一维**的
（深度跨度 vs 一维箱宽）。真正要问的是「跨帧跳变会不会落进**不同的体素**」——
三个空间轴一起分箱时，30 cm 的三维位移可能被摊到三个轴上、哪个轴都不够跨箱，
代理看着够、实际分不开。`scripts/depth_bins.py` 已扩出世界系一节，
**直接跑真正的池化算子**量这件事，不再用代理。

### ⭐ 世界系直测：G4 的机制余量 24.4%，以及一个分箱规则的 bug

不用代理，直接调 `coord_bin_pool` 量「同一 (h,w) 的 K 个 patch，G4 是不是真的
把它们放进了不同的槽」。150 个窗口：

| | 修分箱 bug 前 | **修好后（定稿）** |
|---|---|---|
| **G4 比 G3 多分开的格子** | 24.4% | **28.5%** ✅（判据 ≥10%）|
| 槽位利用率（预算 256） | G3 242 / **G4 63** ⚠️ | G3 242 / **G4 240** ✅ |

**28.5% 比一维代理估的 18% 高**——代理低估了，因为三轴一起分箱时，
一个跨帧位移只要在**任意一个**轴上跨箱就算分开，而代理只看深度那一维。

槽位利用率修好后两组基本齐平（240 vs 242），`enforce_n` 拉平的代价可以忽略，
**"G4 的度量分箱浪费预算"这个担心不成立**——它当初只是一个分箱规则的 bug。

**第二行是个 bug，不是度量坐标的固有性质。** `_resolve_bins` 原本"贪心细化
最粗的轴"，且要求非空箱数**严格增加**（不加这条会死循环）。但占用数随箱数是
**阶梯状**的：

```
[2,2,2,1] → 8 个非空箱    [2,3,2,1] → 8（细一刀没增加）    [2,4,4,1] → 12
```

单步 +1 打不出新格子是常事，贪心就停在平台上。图像网格是密的、细一刀必然多出
格子，所以 **G3 从不触发**；度量坐标的点贴在一层薄壳上，平台到处都是。
后果：`enforce_n` 拉平后三组的公共预算被砍掉四分之三，**且不报任何错**——
所有臂一起变弱，差异被压向 0。

**改成二分搜索一个标量分辨率**，各轴箱数与该轴**物理跨度**成正比
（体素在物理空间里是立方体）。占用数随分辨率单调不减，跨过平台不需要
"每一步都有进展"。顺带三个好处：

1. **t 轴退化也一并修好**：自由细化从旧贪心的 `[7,6,6]`（近乎逐帧、跨帧仅 14%）
   变成 `[4,8,8]`（每箱盖 2 帧）。但 **`n_t` 仍必须显式给定**——理由换了：
   二分的前提是"体素是立方体"，而把 1 帧当成 1 格是任意的，K 或 grid 一变就漂。
2. 物理各向同性本就是度量坐标该有的性质，贪心给的 `[7,6,6]` 在物理上是扁的。
3. 快了六倍（187 → 32 ms/batch，顺带把 `_bin_counts` 的二维 `unique` 换成
   多进制整数键——文件里早有这个快路径，只是当初没接上）。

### ⚠️ 这个脚本的判据本身错了两次

**两次的输出都像"相机模型整个错了"，两次都不是。**

| 第几次 | 判据 | 报出的假误差 | 真相 |
|---|---|---|---|
| 1 | "预测像素处的渲染深度 − 预测深度" | 64.67 / 125.90 cm | `gripper0_grip_site` 在两指之间的**自由空间**，射线穿过去打到桌面。遮挡过滤只挡了"点在表面之后"，没挡"点在自由空间、表面在更远处" |
| 2 | 两相机点云一致性 | 70.17 / 70.05 cm | `read_camera` 把 `CAM="agentview"` 写死在函数体里，**渲染 frontview 的深度却用 agentview 的位姿反投影** |

第二次有个可读的指纹：**两种翻转只差 0.2%**，说明误差与翻转无关，是恒定的
位姿错配——一个"与被检验变量无关的恒定偏差"几乎总是指向测量装置本身。

这是同一类问题的第三次复发（前两次：`probe_vram` 全表假 OOM、真 OOM 被记成崩溃）。
**判据错比结果错更难发现，因为它看起来完全正常。** 成因都写进了对应函数的
docstring。好的一面：三次都在**开跑之前**被拦住，代价是几分钟仿真器时间。

## 8.10 结果十：⚠️ **G2 那一轮训的是单帧** —— 19.6 小时作废（2026-08）

G2 训完 30000 步（`acc=0.527  loss=1.511`），冒烟评测 `FINAL success_rate=0.0000 (0/20)`。
一路查下来，根因不在评测侧：**数据侧的 K 静默退化成了 1**。

### 成因

openvla 的 `RLDSDataset.__init__` 把 `traj_transform_kwargs=dict(window_size=1, …)`
**写死在构造函数里**，外面传不进去。我们只替换了分窗函数（`data/kframe.py`），
拿到的 `window_size` 恒为 1：

    obs_offsets = tf.range(-(window_size - 1) * stride, 1, stride)
                = tf.range(0, 1, 16) = [0]          ← 只有当前帧

**下游没有一处会报错。** `pixel_values` 变成 (B, 6, H, W)，视觉主干照跑，
池化把 256 个 patch 池进 256 个槽（近乎恒等），序列长仍是 302，
loss 从 4.5 降到 1.2，acc 升到 0.53 —— 全部"正常"。
唯一露馅的地方是拿 K=8 的窗口去评测。

`scripts/check_kframe_shapes.py --legacy_patch` 直接测出来的：
`pixel_values (2, 6, 224, 224) → K = 1`。

### 作废的数

| 数 | 原值 | 为什么废 |
|---|---|---|
| G2 训练 acc / loss | 0.527 / 1.511 | 单帧模型的数 |
| `--eval_only` 复核 | 0.638 / 1.216 | 同上 |
| G2 评测成功率 | 0/20 | 模型见过 1 帧、评测喂了 8 帧，不需要别的解释 |
| K=8 微批吞吐表 | 2.7 / 2.4 / 2.4 s，16.3 / 16.9 / 17.9 GB | **全部实测于 K=1** |
| 「4×4 最优」「30k 步 19.7 h」 | — | 建在上面那张表上。真 K=8 是 **4.4 s/步、30k 步 37 h** |
| 「瓶颈在视觉主干不在 LLM」 | — | 那个论证的前提是每步 128 次视觉前向，实际是 16 次（结论方向对，见下） |

不受影响的：深度闸门（8.6）、stride（8.7）、相机反投影（8.8）、
接线挂点验证（8.9，那些张量是自己造的 K=8）、`probe_vram` 的显存表
（它自己构造 K=8 的批，见 8.5）。

### ⚠️ 我一开始把"哪个数能发现它"说反了 —— 重测后的更正

定案当天我写过：`metrics.jsonl` 的 `peak_gb = 16.33`（micro=2）对不上
`probe_vram` 的 19.3 GB，是"一直摆在磁盘上的线索"。**这条不成立。**
真 K=8 重测后：

| 指标 | K=1（作废那轮） | K=8 池化后（重测） | 能否区分 |
|---|---|---|---|
| 峰值显存 | 16.33 GB | **16.6 GB** | ❌ 几乎一样 |
| s/步 | 2.35 | **4.4** | ✅ 1.87× |
| 序列长 | 302 | 294 | ❌ 同量级 |

**池化把视觉块压到 256 个 token，LLM 那一段的序列长与 K 无关；视觉主干又是
冻结的、分 K 次串行前向不留激活 —— 所以 K=8 在显存上几乎免费。**
`probe_vram` 的 19.3 GB 测的是**不池化**的构型（2048 个视觉 token），
那是 G1 的数，本来就不该拿来和 G2 对账。

反过来，我当时还说"吞吐从来没有区分过 K=1 和 K=8"——**也说反了**。
2.35 → 4.4 s/步正是那 8 倍视觉前向的代价，它才是当时真正该起疑的数。

⭐ 这一测顺带把一条一直只有半边证据的说法变成了实测结论：
**池化省的是显存和 LLM 那一段的时间，成本大头（视觉主干）它一点不省。**
K=8 池化后显存与 K=1 持平、时间翻倍 —— 压缩必须靠效果说话，
这一点现在有了 K=1 / K=8 的对照，比原先那句"瓶颈在视觉主干"更准。

### 加的三道闸

| 闸 | 位置 | 拦什么 |
|---|---|---|
| K 自己带进来 | `kframe.patch_strided_chunking(stride, k)` | 不再指望 `window_size`；官方若改成非 1 直接抛 |
| 第一批核对形状 | `finetune_kframe.check_shapes` | `pixel_values` 不是 (B, K*6, H, W) 就退出，并报出实际的 K |
| 交界处对齐 | `coord_pool.coord_bin_pool` | feat 的 token 数与 coord 的坐标数不一致就抛 —— 这一层当时若拦住，19.6 小时就不会白跑 |

外加独立的 `scripts/check_kframe_shapes.py`（不加载模型，30 秒，
带 `--no_patch` / `--legacy_patch` 两个对照）。**开长跑前必跑。**

### 顺带查出来、独立成立的三处

它们不是 0/20 的成因，但都是真问题，已修：

1. **评测没有中心裁**。训练 `image_aug=True` 展开成
   `random_resized_crop(scale=[0.9,0.9])`，模型只见过裁掉外围 5% 的画面；
   评测喂整张 224。修在 `src/common/imgproc.py`（对齐
   `tf.image.crop_and_resize` 的角点对齐双线性），评测默认 `--center_crop True`。
2. **`use_cache=False` 的生成每步重跑整条前向**，投影器被调 1+7 次，
   而 `state` 是一次性的。改成 `set_batch(..., n_uses=N)` 把次数说明白，
   而不是把它改成常驻——"忘了 set_batch 就报错"这条纪律得留着。
3. **诊断脚本自己的夹爪判据错了**。openvla 的 `libero_dataset_transform`
   把夹爪从 −1(开)/+1(关) 变成 `1−clip(g,0,1)` ∈ {0,1}；拿 tfds 的原始动作
   当真值，那一维的真值和标签都是错的。`dataset_statistics.json` 里的
   `grip[+0.00,+1.00]` 早把答案写在脸上，我看了没读懂。

## 8.11 深度缓存的键：三项对拍全过（2026-08）—— ✅

`scripts/check_hash_key.py`，不加载模型、不渲染，G2 训练时并行跑。

| 检查 | 结果 | 不过意味着 |
|---|---|---|
| 训练流的 `img_hash` 都在离线指纹全集里 | **100%**（640/640） | 键对不上，G4 查不到深度 |
| 同一窗口的真实帧指纹互不相同 | 100% | 键是按 episode 编的，会取错帧 |
| 同一窗口的补帧位指纹彼此相同 | 100%（26 个窗口） | 指纹没跟着 gather 走 |

## 8.12 子集判据：`align_stride 1` 让深度闸自己过（2026-08）

`build_subset.py --report_only`，6 条 episode：

| | `--align_stride 2` | `--align_stride 1` |
|---|---|---|
| 深度不确定度 dp95 中位 | 8.1 cm ❌ | **3.9 cm** ✅ |
| dp95 最大 | 9.6 | 4.9 |
| 逐帧 RGB ≤5 的帧占比（中位） | 0.73 | 0.83 |
| 通过 | 0/6 | **4/6** |

`dp95` 几乎正好减半 —— 确认它就是**渲染步长造成的量化地板**（相邻渲染帧隔
stride 个 demo 帧）。**闸按自己的条件过了，一个阈值都没动**，这正是上一轮
预先写死的处置办法：dp95 逼近 5 cm 就减步长，不调阈值。

`dp50` 恒为 0.000、非零占比约 29%：桌面与背景静止，只有机械臂和物体在动。
所以 dp95 量的正是**会动的那些 patch**，也正是 G4 要用的那些。

尺度对照：深度不确定度 3.9 cm ≪ 体素箱宽 ~30 cm（§8.6），
即时间对齐的残差不足以把一个 patch 推进相邻的箱。

剩余 2 条失败全是 **task 9 的「初始帧对不上」**（d0 = 5.75 / 6.41），
与深度无关 —— `no_noops` 削掉的开头超出了 `--demo_frames 40` 的搜索范围
（`check_replay` 早先已记过 task 9 这个现象）。

`--demo_frames 80` 救回其中一条（task 9：0/2 → 1/2），另一条 d0 仍是 6.41。
**不为提高覆盖率去放松 `d0` 的闸**：初始帧对不上就是配错了 demo，
缓存出来的深度属于另一个场景 —— 那正是这道闸存在的理由。

**定稿：`--align_stride 1` + `--demo_frames 80`**（均已改为脚本默认）。
代价：渲染量翻倍，全量从 1–2 h 变成 2–4 h。

⚠️ **覆盖率若按 task 分布不均，要写进论文。** 六组用同一份子集，
跨臂比较不受影响；但某个 task 训练样本变少会让**所有臂**在那个 task 上
一起变差，而评测仍是全 10 个 task。这是数据侧的限制，不是方法的缺陷，
但不能不说 —— 与 §4.2「数据集适用性边界」放在同一节。

## 8.13 G2（真 K=8）冒烟评测 50%，以及评测成本被低估了 3 倍（2026-08）

| | 值 |
|---|---|
| 训练 | 30000 步，总墙钟 **23.3 h**（2.79 s/步稳态，micro=8） |
| 训练末尾 acc / loss | 0.571 / 1.402（8 微批滑动均值，train 模式带增广） |
| `--eval_only` 复核 | **0.618 / 1.243**（eval 模式无增广，方向与幅度都合理） |
| 冒烟评测 n=20 | **10/20 = 50.0%** |

从上一轮的 0/20 到 50%，根因（数据侧 K 退化成 1）与中心裁两处都修对了。
50% 与官方 OpenVLA 在 libero_10 上的 ~53.7% 同量级。
⚠️ **n=20 不构成任何结论**（§3.3：n=50 只能检出 25 个百分点以上的差异）。

### ⚠️ 一个已经可以读、但不构成判据的信号

同一个 `--eval_only` 测量：作废那轮（实为 K=1）**0.638**，这轮真 K=8 **0.618**。
8 帧历史在同 token 预算下并没有让动作 token 预测变好。

不构成判据的两个理由：① token 准确率是弱代理（§8.2 见过 acc 升而成功率降）；
② 那轮不等于 G0 —— 它是 K=1 + 近乎恒等的池化，当前帧独占 256 个 token，
而 G2 的当前帧只有 32 个。但它指向 §3.2 表里的「**G2 ≈ G0 → 前提没成立**」那一行，
先记在这里，等 n=500 的成功率来判。

### 评测成本：20 h/臂，不是 6 h

冒烟 20 局用了 **48 分钟 = 144 s/局**，满量 500 局即 **约 20 h**。
`docs/06` §5 原估 6 h/臂，**低估 3.3 倍**；六臂合计从 34 h 变成 ~120 h，
一举成为整个项目最大的一笔开销。

成本大头是每个动作步 8 次视觉主干前向。**有一个免费的优化**：视觉主干是
冻结的（LoRA 不含视觉），同一帧的特征无论落在哪个窗口里都逐位相同；
而历史窗口里的每一帧都曾是某个时刻的"当前帧"。所以每帧只算一次、缓存复用，
视觉那部分省 8 倍。⚠️ 上线前必须**逐位对拍**（`torch.equal`，不是"看起来一样"），
否则就是在测量环节引入一个不报错的差异。
